## Introduction

Chaque développeur a vécu ça : rejoindre un projet où le style de code est incohérent, des bugs s'infiltrent à cause d'erreurs simples, et les revues de code deviennent des débats de formatage. Ce n'est pas juste agaçant—c'est coûteux.

ESLint et Prettier ne sont pas juste des outils "agréables à avoir" ; ils sont fondamentaux au développement professionnel. Explorons leur impact réel au-delà de la configuration de base.

## ESLint vs Prettier : Différents travaux, même objectif

### ESLint = Qualité du code

ESLint trouve des **problèmes** dans votre code JavaScript :

- Bugs potentiels
- Code smells
- Anti-patterns
- Problèmes de sécurité

### Prettier = Formatage du code

Prettier gère le **style** de manière cohérente :

- Indentation
- Sauts de ligne
- Guillemets
- Espacement

```javascript
// ESLint attrape : variable non utilisée
const unusedVar = "hello"; // ❌ Erreur ESLint

// Prettier corrige : formatage incohérent
const obj = { name: "John", age: 25 }; // ❌ Moche
const obj = { name: "John", age: 25 }; // ✅ Prettier
```

## Le chaos sans outils

### Problèmes réels d'équipe

**1. Enfer des fusions**

```javascript
// Style du Développeur A

}

// Style du Développeur B
function getUser(id) {
  return db.users.find((u) => u.id === id);
}

// Git diff : 90% formatage, 10% logique
```

**2. Gaspillage de revue**

```javascript
// Commentaires de revue de code qui ne devraient pas exister :
// "Ajouter point-virgule"
// "Utiliser des guillemets simples"
// "Corriger l'indentation"
// "Ajouter un espace après if"
```

**3. Bugs cachés**

```javascript
// ESLint attrape ceux-ci immédiatement :
if ((user.isAdmin = true)) {
  // ❌ Assignation au lieu de comparaison

}

  // Instruction de retour manquante

```

## Configuration rapide qui fonctionne vraiment

### Configuration minimale mais efficace

```json
// .eslintrc.json
{
  "extends": ["eslint:recommended", "@typescript-eslint/recommended"],
  "rules": {
    "no-unused-vars": "error",
    "no-console": "warn",
    "prefer-const": "error",
    "no-var": "error"
  }
}
```

```json
// .prettierrc
{
  "semi": true,
  "trailingComma": "es5",
  "singleQuote": true,
  "printWidth": 80,
  "tabWidth": 2
}
```

### Scripts package.json

```json
{
  "scripts": {
    "lint": "eslint src --ext .js,.ts,.jsx,.tsx",
    "lint:fix": "eslint src --ext .js,.ts,.jsx,.tsx --fix",
    "format": "prettier --write src/**/*.{js,ts,jsx,tsx,json,css,md}",
    "format:check": "prettier --check src/**/*.{js,ts,jsx,tsx,json,css,md}"
  }
}
```

## Pièges courants (et comment les éviter)

### 1. Conflits ESLint vs Prettier

```json
// ❌ Règles conflictuelles
{
  "rules": {
    "quotes": ["error", "single"], // ESLint veut des guillemets simples
    "semi": ["error", "always"]     // ESLint veut des points-virgules
  }
}

// ✅ Laisser Prettier gérer le formatage
{
  "extends": ["prettier"], // Désactive les règles de formatage
  "rules": {
    "no-unused-vars": "error" // Garde les règles de qualité
  }
}
```

### 2. Trop de règles

```javascript
// ❌ Ensemble de règles écrasant
{
  "rules": {
    "max-len": ["error", { "code": 80 }],
    "complexity": ["error", 5],
    "max-depth": ["error", 3],
    "max-params": ["error", 3]
    // ... 50 règles supplémentaires
  }
}

// ✅ Se concentrer sur ce qui compte
{
  "rules": {
    "no-unused-vars": "error",
    "no-console": "warn",
    "prefer-const": "error"
  }
}
```

### 3. Ignorer des fichiers importants

```json
// .eslintignore
node_modules/
dist/
build/

// Mais ne pas ignorer :
// src/
// tests/
// config/
```

## Intégration du workflow professionnel

### Hooks pre-commit avec Husky

```bash
# Installer
npm install --save-dev husky lint-staged

# Configuration
npx husky install
npx husky add .husky/pre-commit "npx lint-staged"
```

```json
// package.json
{
  "lint-staged": {
    "*.{js,ts,jsx,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,css,md}": ["prettier --write"]
  }
}
```

### Pipeline CI/CD

```yaml
# .github/workflows/quality.yml
name: Code Quality
on: [push, pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
      - run: npm ci
      - run: npm run lint
      - run: npm run format:check
```

## Règles qui comptent vraiment

### 1. no-unused-vars

```javascript
// ❌ Code mort
const calculateSomething = () => {
  return 42;
};
// Jamais utilisé

// ✅ Code propre
const calculateTotal = (items) => {
  return items.reduce((sum, item) => sum + item.price, 0);
};
```

### 2. no-console (en production)

```javascript
// ❌ Logs de production
console.log("User logged in"); // Expose des données sensibles
console.error("Database error"); // Impact performance

// ✅ Logging approprié
import logger from "./logger";
logger.info("User logged in", { userId: user.id });
```

### 3. consistent-return

```javascript
// ❌ Retour incohérent
function getUser(id) {
  if (!id) return;
  return db.users.find(id);
}

// ✌ Toujours retourner le même type
function getUser(id) {
  if (!id) return null;
  return db.users.find(id);
}
```

### 4. prefer-const

```javascript
// ❌ Réassignation inutile
let name = "John";
name = "Jane"; // Aurait pu être const

// ✅ Immutable par défaut
const name = "John";
const newName = "Jane"; // Variable différente
```

## Techniques avancées

### Règles personnalisées pour votre équipe

```javascript
// .eslintrc.js règles personnalisées
module.exports = {
  rules: {
    // Forcer notre convention de nommage
    "custom/rule-component-name": {
      meta: { type: "suggestion" },
      create(context) {
        return {
          Program(node) {
            // Logique de validation personnalisée
          },
        };
      },
    },
  },
};
```

### Formatage conditionnel

```javascript
// .prettierrc.js
module.exports = {
  printWidth: process.env.NODE_ENV === "production" ? 120 : 80,
  semi: process.env.NODE_ENV === "production" ? false : true,
};
```

## 🔑 Points clés à retenir

- **ESLint trouve les bugs**, Prettier gère le formatage - ils se complètent
- **Automatiser tout** avec les hooks pre-commit et CI/CD
- **Commencer petit** avec des règles essentielles, étendre progressivement
- **Mesurer l'impact** - suivre le temps de revue, les conflits et la réduction des bugs
- **L'adoption par l'équipe** est cruciale - les outils ne fonctionnent que si tout le monde les utilise
- **Se concentrer sur les règles de qualité**, laisser Prettier gérer le style
